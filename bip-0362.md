## Abstract

This document defines four exposure levels for Bitcoin outputs with respect to an adversary
holding a cryptographically relevant quantum computer (CRQC): `EXPOSED_AT_REST`,
`EXPOSED_ON_SPEND`, `NOT_EXPOSED` and `UNDETERMINED`. The first two are BIP 360's long exposure
and short exposure, applied to individual outputs. No deployed output type is `NOT_EXPOSED`.
Levels are derived from confirmed chain data only, so implementations that see the same chain
assign the same levels. An implementation that lacks the data to establish a level assigns
`UNDETERMINED`.

## Motivation

Published estimates of the supply exposed to a CRQC range from about 25% to over 34%. The
difference comes from definitional choices that are rarely stated:

- A reused script that has been spent from and still holds funds. Its key is on the chain, but
  some tools report it as exposed only when next spent.
- P2TR. The output key is a public key, but some tools treat the output as protected because the
  internal key is hidden.
- P2SH and P2WSH outputs whose script has not been revealed.
- Keys disclosed off-chain, for example through an xpub or a spend on a fork.

BIP 360 lists which output types are vulnerable to long exposure and notes that other types
become vulnerable once their script reveals a public key. It does not specify, for a given
output, what counts as revealed or what to report when the history is incomplete. A holder
checking an address, or a custodian deciding which outputs to move first, needs every tool to give
the same answer for the same output.

This document specifies those rules, with test vectors. It does not score risk or recommend when
to migrate. Appendix A gives an informative minimum action for each level.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", and "MAY" in this document
are to be interpreted as described in RFC 2119.

### Terminology

* **Public key**: a point on secp256k1, encoded as compressed (`02`, `03`), uncompressed (`04`),
  hybrid (`06`, `07`) or x-only ([BIP 340](bip-0340.mediawiki)). An x-only key covers both
  points with its x-coordinate.
* **Published**: included in a confirmed transaction, in a `scriptPubKey`, a `scriptSig` or a
  witness.
* **Disclosed**: an output is disclosed if it meets the structural or derived condition of
  `EXPOSED_AT_REST`.
* **Long exposure** and **short exposure**: the two attacks defined in
  [BIP 360](bip-0360.mediawiki), on public keys that are on the chain and on public keys that are
  in the mempool while a spend is unconfirmed.

Unconfirmed transactions and stale blocks MUST NOT be used to determine an exposure level.
Disclosure in them is not a property of the chain and may never become one. Implementations MAY
report it separately; see [Out-of-Band Disclosure](#out-of-band-disclosure).

### Exposure Levels

Each output has exactly one level.

#### `EXPOSED_AT_REST`

A quantum adversary can derive a private key offline and spend the output at any time, with no warning
to the owner. This is BIP 360's long exposure for a single output.

An output is `EXPOSED_AT_REST` if it is disclosed, that is, if either condition holds:

1. **Structural**: its `scriptPubKey` contains a public key.
2. **Derived**: a confirmed transaction has revealed what the output's `scriptPubKey` commits to:
   * for the bytes `S` of a redeem script or witness script revealed by a spend, the output is
     P2SH with script hash `HASH160(S)` or `HASH160(0x0020 ‖ SHA256(S))`, or P2WSH with program
     `SHA256(S)`;
   * for a leaf script revealed with its Merkle path by a P2TR or P2MR script-path spend, whatever
     the leaf requires and however the spend executed, the output is P2MR with root equal to the
     leaf hash or to a branch hash computed along that path as in [BIP 360](bip-0360.mediawiki);
   * for one of the six encodings `e` of the two points with a published key's x-coordinate
     (compressed, uncompressed and hybrid), the output is P2PKH or P2WPKH with key hash
     `HASH160(e)`, or P2SH with script hash `HASH160(0x0014 ‖ HASH160(e))`.

The condition matches hashes only. Nothing is rebuilt from published keys: a script that has not
been revealed does not match, even when every key it needs is published, and the order of the
transactions does not matter. The P2MR match does not examine the leaf: BIP 360 defines no
post-quantum opcode, so no revealed leaf can require one today. Once a leaf can, this match will
over-report for such leaves.

An output that meets the derived condition MUST NOT be assigned a lower level than one that meets
the structural condition. Where the spends themselves are not retrieved, a positive count of
confirmed spends of the output's `scriptPubKey` also establishes this level; see
[Classification Under Partial History](#classification-under-partial-history).

#### `EXPOSED_ON_SPEND`

The output is not disclosed, and spending it is assumed to publish a public key. There is no
offline attack. The exposure window opens when a spending transaction is broadcast and closes when
that transaction is confirmed and buried. An adversary who derives the key within the window can
replace the transaction. This is BIP 360's short exposure. The level does not rule out that the
adversary could rebuild the output's script from published keys; the derived condition does not
attempt that.

Outputs that pay the same `scriptPubKey` share one window. It opens when a spend of any of them is
broadcast and closes when the spend of the last remaining one is confirmed and buried. Once a
confirmed spend has revealed what the script commits to, the other outputs paying the script, and
any paid to it later, are `EXPOSED_AT_REST`. Unconfirmed spends do not change a level.

#### `NOT_EXPOSED`

The consensus rules of the output's type require a valid post-quantum signature on every spending
path. A hybrid scheme that also requires a secp256k1 signature qualifies; a path that can be
satisfied without a post-quantum signature does not, nor does one that needs no signature at all.
A derived secp256k1 private key alone cannot spend such an output, so neither attack applies, and
the level holds even where a condition of `EXPOSED_AT_REST` is met. This level is a property of
the output type. It MUST NOT be inferred for a hash-committed script from the absence of
information about the script.

No deployed output type qualifies. P2MR ([BIP 360](bip-0360.mediawiki)) does not: its consensus
rules allow leaves that can be satisfied without a post-quantum signature. The level exists for
future output types built on post-quantum signature schemes.

#### `UNDETERMINED`

The implementation does not recognize the output's script semantics, or lacks the data to establish
another level, so no sound statement about the output's public keys can be made. An output that
cannot be classified MUST be assigned `UNDETERMINED`, never `NOT_EXPOSED`. Outputs of types
deployed after an implementation's release fall here, as do outputs whose history the
implementation cannot check; see
[Classification Under Partial History](#classification-under-partial-history).

### Conservative Assignment

Implementations MUST apply the **fail-closed rule**: a level other than `UNDETERMINED` MUST NOT be
assigned unless the available data establish its condition, and where they establish none,
`UNDETERMINED` MUST be assigned. Under-reporting gives false assurance; `UNDETERMINED` costs at
most an unneeded migration. The rule accepts the second error to avoid the first.

Consequences:

* A script parse failure MUST NOT clear a level established by other evidence.
* Truncated or partial history MUST NOT yield `NOT_EXPOSED`; see
  [Classification Under Partial History](#classification-under-partial-history).
* Output types the implementation does not recognize MUST yield `UNDETERMINED`.
* `NOT_EXPOSED` is assigned by output type only. It MUST NOT be inferred from the contents of an
  unrevealed script.

### Classification by Output Type

The table gives the level of an output that no earlier transaction has disclosed. The derived
condition overrides every row.

| Output type | On-chain commitment | Level absent prior disclosure |
| --- | --- | --- |
| P2PK | public key, in full | `EXPOSED_AT_REST` |
| P2MS (bare multisig) | all `n` public keys, in full | `EXPOSED_AT_REST` |
| P2PKH | `HASH160` of the key | `EXPOSED_ON_SPEND` |
| P2WPKH | `HASH160` of the key | `EXPOSED_ON_SPEND` |
| P2SH | `HASH160` of the redeem script | `EXPOSED_ON_SPEND` |
| P2WSH | `SHA256` of the witness script | `EXPOSED_ON_SPEND` |
| P2TR | 32-byte x-only output key | `EXPOSED_AT_REST` |
| P2MR ([BIP 360](bip-0360.mediawiki)), where BIP 360 is active | 32-byte script tree Merkle root | `EXPOSED_ON_SPEND` |
| Other witness versions / programs | undetermined | `UNDETERMINED` |
| Non-standard or unparsable | undetermined | `UNDETERMINED` |

**P2TR is `EXPOSED_AT_REST`, including script-path-only outputs.** The output key
`Q = P + H(P‖m)·G` is in the `scriptPubKey`. An adversary who computes the discrete logarithm of
`Q` can sign a key-path spend. Consensus does not check how `Q` was constructed, so a provably
unspendable (NUMS) internal key does not prevent this. `Q` alone does not reveal a BIP 341
output's internal key `P` or script tree, but neither limits key-path spending (see Rationale).
Implementations MAY report a holder-retained secret such as `P` as a separate attribute; they MUST
NOT let it lower the level.

**P2SH and P2WSH are `EXPOSED_ON_SPEND`.** The script is unknown until spent. A spend reveals it,
together with any public keys its signatures require. A revealed script that needs no signature
leaves every other output committing to it spendable by anyone, so those outputs are
`EXPOSED_AT_REST` as well. Before the spend, the script's contents cannot be observed and MUST
NOT be assumed.

**P2MR is `EXPOSED_ON_SPEND`.** P2MR has no key path, so no public key is on the chain before a
spend: it is not exposed at rest. A script-path spend publishes the leaf script and its Merkle path
and, if the leaf requires a signature, a secp256k1 signature and the key it verifies against.
While the spend is unconfirmed, an adversary who derives the key can spend the same output through
the same leaf, as with P2WSH. BIP 360 states that P2MR resists long exposure, and that resistance
to short exposure requires post-quantum signatures. The leaves of an unspent tree cannot be
observed, so an implementation MUST NOT assume a leaf that requires no signature.

A confirmed script-path spend reveals the leaf script and its Merkle path, so every other output
committing to the same tree is `EXPOSED_AT_REST` by the derived condition, whatever the leaf
requires. A published leaf key alone does not disclose a P2MR output, because spending it also
requires the leaf script and Merkle path.

A P2MR output whose tree has depth zero can be spent by anyone once its leaf has been revealed,
since BIP 360 skips script execution at depth zero; like any other output committing to a
revealed script that needs no signature, it is `EXPOSED_AT_REST`. Before BIP 360 activates, a
witness version 2, 32-byte output can be spent without any key, which is not exposure to a
quantum adversary; its level describes it as P2MR after activation, and implementations SHOULD
flag the case separately, in addition to the level.

### Classification Under Partial History

These rules apply to types whose level depends on spend history, those that are otherwise
`EXPOSED_ON_SPEND`. Structural levels need no history: P2PK, P2MS and P2TR are `EXPOSED_AT_REST`
from the `scriptPubKey` alone, and an unrecognized type is `UNDETERMINED` whatever its history.

An implementation may be unable to retrieve a script's complete history, because of indexer
pagination, scan limits or pruning. An aggregate count of the script's confirmed spent outputs,
where available, is sufficient for `EXPOSED_AT_REST`.

If the count is greater than zero, at least one confirmed spend has occurred. For every type in
the table other than `UNDETERMINED`, a spend reveals what the script commits to: the key, the
script, or the leaf with its Merkle path. All of its outputs are therefore `EXPOSED_AT_REST`,
P2MR included. A count of zero establishes only that no output paying this `scriptPubKey` has a
confirmed spend.

Transactions that the implementation does retrieve cannot lower a level the count has
established. A revealed script that needs no signature is no exception: the other outputs
committing to it can be spent by anyone.

A count of zero does not establish `EXPOSED_ON_SPEND`, because the key or script may have been
published under another `scriptPubKey`. `EXPOSED_ON_SPEND` requires that the derived condition has
been checked against every confirmed transaction and is not met. An implementation that can
establish neither level MUST assign `UNDETERMINED`.

### Indexer Blind Spots

Address-indexed data sources index outputs by the address encoded in their `scriptPubKey`. P2PK
and bare P2MS outputs have no address and are often missing from the history of the P2PKH, P2WPKH
or P2SH-P2WPKH address for the same key, so such a source cannot show whether the key has been on
the chain since 2009. An implementation that relies on it can establish `EXPOSED_AT_REST` from a
positive spend count, but not `EXPOSED_ON_SPEND`, and MUST assign `UNDETERMINED` where the count
is zero. Implementations SHOULD also query an index of published keys where one is available, and
MUST document the limitation where none is.

### Out-of-Band Disclosure

The following disclose public keys without evidence on the Bitcoin chain and are outside this
classification:

* a transaction that was broadcast but never confirmed, or was replaced;
* a block that is not in the best chain, such as a stale block;
* spends on a fork that shares Bitcoin's UTXO history;
* an extended public key given to a third party, which reveals every public key derivable from it,
  including keys of outputs never spent;
* reuse of the key on sidechains, bridges or other protocols;
* compromise or publication by anyone holding the key.

The levels describe only what the chain shows. A level of `EXPOSED_ON_SPEND` or `NOT_EXPOSED` is
therefore not evidence that no disclosure has occurred, and implementations MUST NOT report it as
such. Implementations that learn of such disclosure by other means SHOULD report it as a separate
signal, labelled as not chain-derived.

## Rationale

**Four exposure levels.** A binary exposed/not-exposed flag would lump long-exposure and
short-exposure targets together into one bucket. `EXPOSED_AT_REST` outputs are a more urgent target
for migration, as they are more likely to be viable targets sooner than `EXPOSED_ON_SPEND` outputs,
and any exposure classification system ought to specify the distinction between them. `UNDETERMINED`
is required by the fail-closed rule, not by a difference in risk.

**A level with no members.** `NOT_EXPOSED` has no member today. Defining it now fixes its meaning,
a property of consensus rules and never an inference about an unseen script, before an output type
that needs it exists.

**Disclosure mechanism does not change the level.** Structural and derived disclosure give the
adversary the same capability. Separate levels would suggest that a reused address is safer than
P2PK. Implementations that report the mechanism SHOULD do so as a separate attribute, not by
lowering the level.

**Beyond the spent output.** A simpler rule would disclose only outputs whose own `scriptPubKey`
has a confirmed spend. It would miss exposures that need no search: the genesis coinbase key is in
a P2PK output while its P2PKH address holds tens of thousands of unspent outputs at the time of
writing, one witness script can be paid through both its P2WSH and P2SH-P2WSH forms, and BIP 360
describes moving script trees from P2TR to P2MR, where a leaf revealed by a P2TR spend then opens
the P2MR output. The rule stops at hashes that follow directly from what a spend revealed. A
search through combinations of published keys could open further scripts. No level claims that
it could not.

**Attacker-spendability, not holder-provability.** The classification describes what an adversary
can do under current consensus rules, which is observable. Whether the holder retains a secret the
adversary lacks, such as a P2TR internal key, is not: a tweaked `Q` cannot be distinguished
on-chain from a bare key. A classification based on it could not be deterministic, and a recovery
mechanism based on it would fail for an unknown fraction of P2TR outputs. Holder-provability
belongs in a rescue protocol specification.

**No scoring.** A risk score depends on balance, dormancy and CRQC timelines, which are contested
and not observable on-chain. Standardizing only the observable makes independent results
comparable.

**Chain data only.** Mempool contents and stale blocks differ between nodes and change over time,
so a level based on them could not be reproduced later. An implementation that cannot see the
whole chain assigns `UNDETERMINED` where it cannot decide, so it never contradicts one with
complete data.

**The aggregate count.** The full history of a heavily used script is long, and many light clients
cannot retrieve it. A count of confirmed spends is one query, and a positive count establishes
`EXPOSED_AT_REST` by itself, so a scan that stops before the first spend still reports it.

**Relationship to BIP 361.** BIP 361 defines its phases over output types, which consensus can
evaluate. This document answers a per-output question that consensus does not: whether the key of
a given output has already been published. Neither depends on the other.

**Relationship to BIP 360.** BIP 360 defines the two attacks and lists which output types are
vulnerable to long exposure; the table in
[Classification by Output Type](#classification-by-output-type) starts from that list. BIP 360 also
defines P2MR, which is not exposed at rest and is `EXPOSED_ON_SPEND` because an unrevealed tree may
contain a secp256k1 leaf. This document requires BIP 360 for its terms and for P2MR. The rest
applies if BIP 360 is not activated.

## Appendix A: Holder Implications (Informative)

For each level, the table gives the minimum action a holder should be advised to take and a fixed
action key. Implementations MAY report the action key alongside the level so that wallets give the
same baseline advice. Implementations SHOULD NOT give advice that contradicts the table. Wording,
reasons and urgency are left to them.

| Level | Action key | Minimum advice |
| --- | --- | --- |
| `EXPOSED_AT_REST` | `MIGRATE` | Move the funds to an output type that is not exposed at rest as soon as one the holder trusts is available. Until then, do not add funds to the output. |
| `EXPOSED_ON_SPEND` | `SWEEP_WHEN_SPENDING` | Stop giving out the address for new payments; no other action while unspent. When spending, spend every output paying the same script in one transaction, and do not send change or new funds back to that script. |
| `NOT_EXPOSED` | `NONE` | No action. |
| `UNDETERMINED` | `MIGRATE` | As for `EXPOSED_AT_REST`, until the implementation can classify the output. |

The `EXPOSED_AT_REST` advice names a property, not an output type. Hash-committed outputs with no
prior disclosure, including P2MR ([BIP 360](bip-0360.mediawiki)) once available, are not exposed at
rest. They are `EXPOSED_ON_SPEND`, and that advice then applies. Implementations SHOULD state which
destinations they consider available, and SHOULD NOT describe any of them as `NOT_EXPOSED`.

## Backward Compatibility

This document introduces no consensus, policy or peer-to-peer change. Software that reports
exposure under another taxonomy changes in three ways on adoption, all in the conservative
direction:

* reused scripts whose earlier spends published their keys, and that retain a balance, move to
  `EXPOSED_AT_REST`;
* unrecognized output types move to `UNDETERMINED`;
* for software that followed versions of this document before 0.5.0, P2MR outputs move from
  `NOT_EXPOSED` to `EXPOSED_ON_SPEND`.

Implementations SHOULD version their reports so that consumers can distinguish results produced
before and after adoption.
