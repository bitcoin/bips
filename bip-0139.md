## Abstract

This document specifies a format for exporting wallet backup data, including accounts,
descriptors, associated keys, labels, transactions, and partially signed Bitcoin
transactions (PSBTs).
The format aims to standardize wallet backup and restore operations across different
Bitcoin wallet implementations by providing a common structure and field naming
conventions.
Each object structure defines a few mandatory fields; all other fields are optional.
The base structure must include at least one account entry.

The optional fields of the format are collected in a companion
[field registry](bip-0139/field-registry.md), which acts as a central repository where
a wallet implementer can register their usage of a field and share that usage through a
test vector.

## Motivation

Bitcoin software wallets store various forms of metadata beyond just private keys,
including account structures, descriptors, labels, and transaction history.  
While [BIP-0039](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)
and [BIP-0032](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki) provide
standardized mechanisms for key recovery, they do not preserve additional wallet-specific
metadata necessary for seamless migration between wallets.

A standardized wallet backup format ensures that users can migrate wallets without losing
critical metadata, reducing vendor lock-in and enabling more robust recovery options.

## Rationale

Several wallet implementations store backup data in proprietary formats, making migration
difficult.  
This proposal introduces a structured format, leveraging JSON to store wallet
metadata in a portable way.  
The format is flexible and extensible, allowing wallet developers to include as much
or as little information as they think necessary.  

By keeping the mandatory set of metadata small and keeping every other field
optional, this spec accommodates diverse use cases and preferences.  
Wallet developers can include only the fields relevant to their software while
maintaining structural integrity.  

## Specification

A wallet backup is a UTF-8 encoded text file containing a single valid JSON object
representing the backup structure.  
This object includes wallet-level metadata, multiple accounts, and associated key
data.

### Field Registry

The optional fields of every object structure are collected in the
[field registry](bip-0139/field-registry.md) rather than in this document, so new
fields could be added without amending this BIP.  
Only optional fields are registered; making a field mandatory is a change to this BIP
and increments the format version.  
Registration of a new field must state the field name, the object it belongs to,
its type, and a short description, and should link a test vector or an implementation
using it when available.  
A field name must not conflict with an already registered field of the same object.  

### Wallet Backup Structure

The top-level JSON object must contain the `version` field and at least one account in
the `accounts` array.  
All other fields are optional and listed in the
[field registry](bip-0139/field-registry.md).  

- `version`: Mandatory string identifying the backup format and its version.  
  Must be `BIP139-<version>`, where `<version>` is an integer.
  The version is incremented only for changes that are not backward compatible, such
  as adding a mandatory field.  
- `accounts`: Mandatory array of account objects.  
  Must contain at least one account.  
  See [Account Object Structure](#account-object-structure).  

### Account Object Structure

Each account object in the `accounts` array represents a single account within the
wallet and must contain the `type` and `descriptor` fields.
All other fields are optional and listed in the
[field registry](bip-0139/field-registry.md), allowing wallets to include only the
metadata they support.

- `type`: Mandatory string describing the account type.  
  Must be one of `bip_380` (output descriptor), `bip_388` (wallet policies), or
  `bip_392` (silent payments).  
- `descriptor`: Mandatory string representing the account structure as defined by the
  value in `type`.  

### Key Object Structure

Keys in the `keys` dictionary are indexed by their
[BIP32 fingerprint](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki#key-identifiers).
Each key object contains metadata about the key and must contain the `key` field.
All other fields are optional and listed in the
[field registry](bip-0139/field-registry.md).

- `key`: Mandatory string representing the public key fingerprint in hexadecimal
  form.

### Transaction Object Structure

Each entry in the `transactions` array is a JSON object describing a single transaction
relevant to the account and must contain the `txid` field.
All other fields are optional and listed in the
[field registry](bip-0139/field-registry.md).

- `txid`: Mandatory string containing the transaction id (hex).  

### Silent Payment Owned Output Object Structure

Each entry in the `bip352_outputs` array is a JSON object describing a single output
owned by the account and must contain the `outpoint` and `tweak` fields.
All other fields are optional and listed in the
[field registry](bip-0139/field-registry.md).

- `outpoint`: Mandatory string representing the outpoint in the form `<txid>:<vout>`.  
- `tweak`: Mandatory hexadecimal string representing the tweak.  

## Importing

When importing a wallet backup follow these guidelines.  

* Software should validate the structure, ensure at least one account is present, and
  check that every object carries its mandatory fields before attempting import.  
* Software, during import, should preserve all metadata it supports and discard
  unsupported fields.  
* Software should warn users if essential data cannot be restored.  
* Wallets may truncate labels or other string fields if necessary, but should warn
  users when truncation occurs.  

## Encryption

This format can be encrypted following [BIP-138](https://github.com/bitcoin/bips/pull/1951).

## Security Considerations

* The backup format should not include private keys to avoid unintended key exposure.  
* Backups should be encrypted to prevent unauthorized access.  
* Care should be taken to ensure that proprietary metadata does not contain sensitive
  information.  
* Since backups may be stored online or in cloud storage, mnemonics and private keys are
  intended for test networks only (`testnet3`, `testnet4`, `signet`, `regtest`); they MUST NOT
  be used to store mainnet secrets.  

## Backwards Compatibility

This format is extensible and allows future additions without breaking compatibility.  
Wallets may ignore fields they do not recognize while maintaining the structural
integrity of the backup.  
New fields are added through the [field registry](bip-0139/field-registry.md), and
wallets should gracefully handle unknown entries by ignoring them.
